# Voyage Architecture

## Product boundary

Voyage and CrewCheck are separate products. Shared capabilities happen through explicit, versioned APIs/contracts. Voyage never imports CrewCheck parsers or canonical roster internals directly.

## Runtime

- `voyage-api` — Node service for Render.
- `app/www` — premium responsive web shell and PWA.
- Capacitor — Android packaging layer generated in CI.
- TiDB Cloud — Voyage application database.

## Core domain

```text
TravelSource
  -> DocumentNormalizer
  -> TravelEntityExtractor
  -> ReservationMatcher
  -> TripGraph
```

Every travel fact carries provenance, confidence and freshness. AI may interpret or summarize facts, but it must not invent operational travel state.

## Identity and Google

Google Login and Gmail access are deliberately separate grants:

- Login: `openid email profile`
- Gmail travel import: `gmail.readonly`

The Gmail grant is optional and incremental. Render placeholder values such as `value` are treated as **not configured**.

## Availability

Both passengers and crew members explicitly state how many days they want to use.

- `PASSENGER`: user provides desired days/date flexibility.
- `CREW_MEMBER`: Voyage may consume a future CrewCheck availability API, but still asks how many days the user actually wants to use.

Crew availability must preserve source version, freshness and operational margins.

## Mobile

The Android project is generated by GitHub Actions from the Capacitor configuration. The workflow builds a debug APK without requiring production signing secrets. Production signing will use GitHub Secrets and a dedicated release workflow later.
